# Set Ontology

Changes an asset's **ontology** (`exo__Asset_isDefinedBy`) after creation, and
moves the file into the new ontology's folder so the co-location invariant keeps
holding.

Click → a one-field form (`Ontology`, a fuzzy reference-picker over
`exo__Ontology` instances) → the asset is re-anchored and relocated. Cancelling
the form is a no-op.

Composite ([[170d1f56-235a-4dfb-b473-ec90595d3bfe|Set Ontology (composite)]]) of
two ordered steps:

1. **Re-anchor** ([[1585f1cb-7871-4a7c-809c-f89a57444e38|step 1]], `property_set`)
   — `exo__Asset_isDefinedBy` ← `$input.ontology`.
2. **Relocate** ([[08da54cf-a587-4cf2-a144-ea195fd6cf66|step 2]], `service_call`
   `repairFolder`) — moves the file into the picked ontology's folder.

## Why this command exists

Re-anchoring was reachable **only from the CLI** — `set-property
exo__Asset_isDefinedBy …` (which even prints a co-location warning telling you to
run `apply repair-folder` afterwards), i.e. two manual steps and no UI at all.
The only in-app paths were the *hard-wired* ones: «Archive Ontologically»
(→ the ontology's declared archive ontology), «Un-archive Ontologically» and
«Cold Archive». There was no way to say «put this asset into **that** ontology».

Nothing new was built in the engine for this — it is an *emergent composition*
of already-shipped grounding primitives (`property_set` + `service_call
repairFolder` + `composite` + `assetRef` form field), exactly like the archive
composite it mirrors.

## Scope

Bound to `exo__Asset` (universal, `maintenance` group, order 215 — right after
«Repair Folder», its closest sibling). No precondition: any asset may legitimately
be re-anchored.

`exocmd__Command_destructive: true` gates the **CLI** path only (`apply` then
requires `--yes`); it does not add a confirm dialog in the plugin, where the form
itself is the gate. This is deliberate — `confirmMessage` fires *before* the
form, which would ask «are you sure?» before the user has even picked a target.

## CLI — mind the value form

```bash
exocortex apply set-ontology <path> --vault <v> \
  --input '{"ontology":"\"[[<ontology-uid>]]\""}' --yes
```

⛤ The `ontology` value must be the **quoted** wikilink — the two characters `"`
are part of the string, hence the escaping inside the JSON. This is not
decoration: `targetValueSubstitution` writes the substituted value **verbatim**,
and the plugin's `ReferencePicker` commits exactly that quoted form
(`toReferenceWikilink` → `"[[<uid>]]"`), which is what makes the picker compose
with this grounding at all.

⛔ Passing the natural-looking bare form `'{"ontology":"[[<uid>]]"}'` **fails
silently**: unquoted `[[uid]]` is YAML flow-sequence syntax, so
`NoteToRDFConverter` emits the object as a **literal** `"<uid>"` instead of the
file-IRI `obsidian://vault/…/<uid>.md`. Verified on a scratch vault — the command
still reports success and `repairFolder` still relocates the file (its resolver
is tolerant), but the asset is now invisible to every graph join over
`exo__Asset_isDefinedBy`. Commands built on `targetValueRef` (e.g. `set-blocker`,
`set-parent`) take a **bare** UID instead, because that path wraps the value
itself — see step 1's note for the full contrast.

Follow-up for the CLI ergonomics gap (normalize both forms, or reject the
ambiguous one loudly): `ems__Task` [[34376823-9fc2-44a1-a5cf-7ae07afce4e3]].

## Known failure mode

`repairFolder` refuses to overwrite: if an asset with the same basename already
exists in the destination ontology's folder, step 2 throws `Cannot move file:
<path> already exists`, the composite rolls back and the asset keeps its original
ontology and location. This is reachable in practice — basename collisions across
assetspaces do occur in this vault — and it is the safe outcome (no data loss),
but the message is engine-level plumbing surfacing to someone who just picked an
item from a dropdown.

## Verification

Round-trip exercised end-to-end on an isolated copy of `vault-exodev` (real
engine, real TBox), both directions between `$exodev` and `$exocmd`: frontmatter
re-anchored, file physically relocated, and the emitted triple confirmed to be
the ontology's **file-IRI**. Revert-verified on three independent axes — drop the
binding → the button disappears from `resolve-buttons`; omit `--input` → step 0
fails loud with no partial write; swap step 1 to `targetValueRef` → step 1 writes
an unresolvable value, step 2 fails and the composite rolls back.
