# Create action

Grounding bound to the "Create Action" command (`48a70029`). Creates a new
`ems__Action` via the declarative `create_instance` pipeline — full sibling of
the "Create task" grounding (`a222094b`), only the target class differs
(`ems__Action` instead of `ems__Task`).

- `targetClass` → `ems__Action` (`6a99d2ca`).
- PropertyDefault `d9aa9bb8`: new Action starts as `ems__EffortStatusDraft`
  (same default as Create Task).
- InheritanceRules declared here: `3f08f5a8` (Area target → `ems__Effort_area`)
  and `cbe000c4` (unconditional `exo__Asset_isDefinedBy` pass-through).

## Where `ems__Effort_parent` comes from

⚠ **Deliberately NOT declared on this grounding.** Both parent rules are
inherited from the Universal Default Template (`62907ff4`):

| Target class | Rule | Result |
|---|---|---|
| `ems__Project` | `01f570c9` (universal) | `ems__Effort_parent` = the project |
| `ems__Task` | `65acce2f` (universal, since 2026-09-09) | `ems__Effort_parent` = the task |
| `ems__Area` | `3f08f5a8` (this grounding) | `ems__Effort_area` = the area |
| prototypes, any other class | — | no parent, no area — by design |

The reason is mechanical, not stylistic: `mergeInheritanceRules` deduplicates by
`targetPropertyName`, so a grounding can carry **at most one** rule per property,
and that one also shadows every universal rule for the same property. Declaring
`43731bae` here would therefore make the Task rule unreachable (and vice versa) —
measured on a vault copy. Two condition-based sibling rules can only coexist on
the Universal Template. See `65acce2f` for the full measurement table.

⚠ Before 2026-09-09 this grounding declared `43731bae` and its body claimed
"Project/Effort target → parent". That was wrong for every class except
`ems__Project`: `ems__Task` targets produced an Action with **no**
`ems__Effort_parent` at all. Fixed by moving parent inheritance to the Universal
Template (founder interview 2026-09-09, decision #2; subject
`0e914ac3-64bd-4e13-896a-d64b3a3e8d30`, GitHub issue `kitelev/exocortex#4220`).
The ontology moved first: the range of `ems__Effort_parent` (`6528ecfa`) was
widened from `ems__ParentEffort` to `ems__Effort` in `exoas-public`, since
`ems__Task` is not a `ems__ParentEffort`.

`43731bae` itself is untouched and still declared by the five other
effort-creating groundings.

Prototype targets deliberately keep falling through every parent rule — their
relation to the created instance is the `exo__Asset_prototype` back-link the
executor writes (regression guard for the 2026-05-24 defect that narrowed
`43731bae` in the first place); the command's precondition `365095bc` refuses
prototype targets outright.
