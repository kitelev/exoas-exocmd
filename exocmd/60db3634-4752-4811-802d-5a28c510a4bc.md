Основание типа `property_replace` для **точечной замены** класса в `exo__Instance_class`.

## Зачем отдельное основание

`exo__Instance_class` **guarded** в CLI: `set-property` отвечает fail-loud
«has a dedicated guarded command … Use: exocortex apply convert-to-task|convert-to-project».
Гвард верен — реклассинг есть семантическая операция. Но перечисление слоёв (замер 2026-09-21)
показывает, что нужной операции нет ни на одном из них:

- `convert-to-task` / `convert-to-project` — **ЗАМЕНЯЮТ** класс, но только для `ems__Task` /
  `ems__Project`; к метаклассу TBox-свойства неприменимы;
- `append-instance-class` (`e258207a`, основание `ac0cf4ce`, тип `property_append`) —
  **ДОПИСЫВАЕТ** аддитивно, исходный класс не снимает;
- raw `Write`/`Edit` — блокируется `dogfood-cli-mutation` (`instance_class` в guarded-списке).

`property_replace` (req `02de55a4`, Active, v16.244.1) — ровно эта операция: снять один
элемент списка и поставить другой, не тронув со-значения и их порядок.

## Форма

    exocmd__Grounding_type: property_replace
    exocmd__Grounding_targetProperty: exo__Instance_class
    exocmd__Grounding_replaceFromExpression: $input.from
    exocmd__Grounding_replaceToExpression: $input.to

Симметрично сиблингу `ac0cf4ce`, который читает `$input.class` — `inputSchema` не нужен,
`apply … --input '{…}'` подаёт JSON напрямую.

## ⛔ Отсутствующий from — ОТКАЗ, не дописывание

Свойство наследуется от типа и является несущим: без него операция вырождалась бы в
`property_append` на каждом промахе и молча давала ассету противоречивую пару метаклассов —
ровно то состояние, против которого и заведён тип.

Требование `0e237a8c-2daa-4c4f-add5-bd8f94080bf8`, issue #4305.
