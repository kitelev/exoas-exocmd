# Repair folder on created instance (step)

`service_call` → `repairFolder`, с `exocmd__Grounding_targetsCreatedInstance: true`.

Пятый и **последний** шаг композита `27a37448` («Create, Execute & Archive»).

## Зачем

Шаг 4 (`83d3b4d5`) переанкеривает созданное действие в архивную онтологию
(`exo__Asset_isDefinedBy` → `9d1d2e9d`), но **файл при этом остаётся в исходной
папке**. Co-location-инвариант требует, чтобы ассет лежал в папке файла своей
онтологии — то есть после переанкеривания действие обязано переехать в
`my-efforts/archived/`. Без этого шага **каждое** созданное действие становится
co-location-нарушением (проверено `audit co-location` на изолированной копии
2026-08-15: созданное действие попадало в список нарушений).

## Почему этот шаг не существовал раньше

`exocmd__Grounding_targetsCreatedInstance` был **инертен для `service_call`**:
сервис резолвит свой файл из переданного IRI (`IGroundingService.execute` не
имеет канала для пути), а переставлялся только `filePath` шага — поэтому сервис
молча работал по клик-таргету и «успешно» ничего не делал. Это issue #4046,
закрытый в PR #4047 (v16.217.3): `executeServiceCall` теперь передаёт сервису
`vaultPathToIRI(filePath)` — и только когда флаг выставлен.

## Почему ПОСЛЕДНИМ

`repairFolder` перемещает файл. Любой последующий шаг писал бы по **старому**
пути — то есть в уже несуществующее место либо, хуже, воссоздал бы файл там.
Порядок здесь несущий, а не косметический.
