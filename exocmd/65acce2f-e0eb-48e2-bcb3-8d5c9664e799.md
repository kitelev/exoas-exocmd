# InheritanceRule: uid→parent (condition: ems__Task, prio 50)

Task-conditioned parent inheritance rule, attached to the **Universal Default Template** (`62907ff4-bf91-4c94-8e02-92b3ca2bc798`) as the sibling of `01f570c9-3bf2-4ec8-af27-0aa4d9cbc29f` ("Universal IR: Project.uid → new.ems__Effort_parent").

**Semantics:** when the target IRI is an `ems__Task` instance, copy the target's `exo__Asset_uid` into the new instance's `ems__Effort_parent` slot.

## Frontmatter

- `_sourceProperty` = `exo__Asset_uid` (`[[fada7446-b0a4-4100-88f4-6d4421c175fb]]`)
- `_targetProperty` = `ems__Effort_parent` (`[[6528ecfa-a03d-47f1-a819-9ba5fea8fc28]]`)
- `_targetClassCondition` = `ems__Task` (`[[1b20a8f0-d745-4e93-91db-4531b3df120e]]`)
- `_priority` = 50

## Engine semantics

Filter pass: the rule applies only if the target IRI is rdf:type `ems__Task` — a **direct** class match via `classRefMatchesAny`, which does **not** walk `exo__Class_superClass`. That directness is load-bearing: `ems__TaskPrototype ⊂ ems__Task`, so a superclass-walking condition would re-introduce the 2026-05-24 defect (prototypes getting a spurious `ems__Effort_parent` pointing at the prototype). Prototype targets keep falling through every parent rule; their relation to the created instance is the `exo__Asset_prototype` back-link the executor writes.

If the filter passes, write `frontmatter['ems__Effort_parent'] = '⟦target-uid⟧'`.

## ⛔ Why it lives on the Universal Template and not on a Grounding

`mergeInheritanceRules` (`packages/core/src/services/UniversalDefaultTemplateResolver.ts`) deduplicates **by `targetPropertyName`**: it builds a `Map` from the grounding's rule list (last entry wins), overrides every same-property universal rule with it, and then skips the remaining grounding rules with that property. Consequence, measured on a vault copy:

| grounding rule list for `ems__Effort_parent` | Task target | Project target |
|---|---|---|
| `43731bae` then a Task rule | parent set | **parent lost** |
| a Task rule then `43731bae` | **parent lost** | parent set |

So **at most one rule per `targetPropertyName` survives in a grounding**, and it also shadows the universal rules for that property. Two condition-based sibling rules (Project + Task) can therefore only coexist on the **Universal Template**, whose own list is not deduplicated against itself. Accordingly, grounding `1bc1e938` ("Create action") carries **no** parent rule at all and inherits both from the Universal Template.

`targetClassCondition` is single-valued (`CommandResolver`), so "Project OR Task" cannot be expressed by one rule; and an unconditional rule plus `targetClassExclusion` was rejected because the "Create Action" precondition admits status-less non-Effort targets (measured: a `concept__Concept` fixture passes it), which would then receive an `ems__Effort_parent` violating the property's range.

## Blast radius

Only "Create Action" changes. Every other grounding that creates efforts (`a222094b` "Create task", `8748f8b0` "Create project", `4919afb1` "Create related task via service", `b7a84c3c`, `d53c8726`) still carries `43731bae` in its own list, which overrides both universal parent rules — measured: `create-task` and `create-project` produce byte-identical results on Task and Project targets before and after this change.

## Why it exists

"Create Action" on an `ems__Task` target used to produce an Action with **no** `ems__Effort_parent` at all — the grounding reused only the Area rule, the Project rule and the isDefinedBy pass-through, and a Task matches none of them. An action created under a task is the most common flow of the executive-assistant loop, so the action silently lost its home.

The ontology had to move first: `exo__Property_range` of `ems__Effort_parent` was `ems__ParentEffort`, which `ems__Task` is not a subclass of, so writing a Task into that slot was a `sh:class` violation. The range was widened to `ems__Effort` on 2026-09-09 in `exoas-public`.
