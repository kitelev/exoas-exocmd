# Re-anchor isDefinedBy to the picked ontology

Step 1 of the «Set Ontology» composite — the **generic** counterpart of
[[af5090bf-304f-4670-acd5-ab5a42f76bd8|Re-anchor isDefinedBy to archive ontology]]
(Archive Ontologically, RFC 78c2b7d0 C5): where that step computes the target
ontology from a NamedQuery (`targetValueQuery`, archive-specific), this one takes
it from the **user's pick** in the composite's `assetRef` form field.

- `exocmd__Grounding_type` = `property_set`
- `exocmd__Grounding_targetProperty` = `exo__Asset_isDefinedBy`
- `exocmd__Grounding_targetValueSubstitution` = `$input.ontology`

⛤ **Why `targetValueSubstitution`, not `targetValueRef`** — the two differ in
whether the executor re-wraps the value:

- `targetValueRef` → `GroundingExecutor.executePropertySet` builds
  `"[[<ref>]]"`, i.e. it wraps the resolved value in brackets itself. It therefore
  expects a **bare UID** (that is why `set-blocker`'s plain-text
  `format: asset-reference` field works with it).
- `targetValueSubstitution` → the substituted value is written **verbatim**.

The `ReferencePicker` behind an `assetRef` form field commits an already-quoted
wikilink (`"[[<uid>]]"`), so pairing it with `targetValueRef` would yield
`"[["[[uid]]"]]"` — a broken link that SHACL does not catch (it is a literal, not
a dangling target). `targetValueSubstitution` is the form that composes with the
picker.

`exo__Asset_isDefinedBy` is not in `STRING_SCALAR_PROPERTIES`, so the value is
written through unquoted-verbatim — exactly the `"[[<uid>]]"` frontmatter form.

Must run **before** the folder-relocation step so `repairFolder` sees the new
`isDefinedBy` (same load-bearing ordering as the archive composite).
