# Set Ontology (composite)

Ordered composite grounding for the «Set Ontology» command — a **generic**
re-anchoring of `exo__Asset_isDefinedBy` after creation, driven by a user pick
instead of a hard-wired target ontology.

1. [[1585f1cb-7871-4a7c-809c-f89a57444e38|Re-anchor isDefinedBy to the picked ontology]]
   — `property_set` `exo__Asset_isDefinedBy` ← `$input.ontology` (the value the
   user chose in the `assetRef` picker below).
2. [[08da54cf-a587-4cf2-a144-ea195fd6cf66|Relocate to ontology folder]] —
   `service_call` `repairFolder` moves the file into that ontology's folder, so
   the **co-location invariant** holds after the change.

Step order is load-bearing: `repairFolder` reads the *already re-anchored*
`isDefinedBy`. Atomic via `GroundingExecutor.executeComposite` rollback on step
failure.

⛔ **`repairFolder` must remain the LAST step.** `GroundingExecutor.rollback`
restores the original content to the **pre-composite path** — the path captured
before any step ran. That is safe here only because nothing executes after the
move: the step loop breaks on the first failure, so a successful relocation is
never followed by a failing step. Append a step 3 and the guarantee inverts — a
failure there would recreate the source at the *old* path while the moved file
still sits at the *new* one, leaving **two** half-correct copies. The atomicity
of this composite is a property of its step ORDER, not of the rollback mechanism.

## Form

`exocmd__Grounding_inputSchema` declares a single `assetRef` field —
`ontology`, `targetClassUid` = `829b9b3b-…` (`exo__Ontology`) — so the picker
lists only ontology anchors (107 of them in `vault-exodev` at the time of
writing; `findAssetRefCandidates` matches `exo__Instance_class` by class UID or
label, and the anchors declare the UID form).

`CommandExecutionFlow` opens the form for **any** grounding carrying an
`inputSchema` (not just `create_instance`), and `executeComposite` threads the
collected `UserInput` into every step, so step 1 sees `$input.ontology`.

⛤ The `inputSchema` lives on **this composite** — `CommandExecutionFlow`
reads `rc.command.grounding.inputSchema`, i.e. the top-level grounding only.
Putting it on the step would silently open no form and step 1 would fail loud
with «value template references an input that was not provided».

⛤ The raw frontmatter value here is a JSON *object*, but
`CommandExecutionFlow.extractInputSchema` requires an *array* — the conversion
happens earlier, in `CommandResolver`, which parses the JSON schema into the
array of field descriptors and propagates `title` → label, `required`, and
`targetClassUid` verbatim.

## Reuse of step 2

Step 2 is the **existing** `service_call repairFolder` grounding
`08da54cf` (labelled «Relocate to archive ontology folder» because it was
authored for the archive composite). It carries no archive-specific data — the
`serviceId` is simply `repairFolder`, which reads whatever `isDefinedBy` the
previous step wrote. «Cold Archive» (`4fba7a3a`) reuses the very same step for
the same reason; this is the established pattern, not a shortcut.

## Precedent

Structural twin of [[ee48c626-ce92-43f9-b7b6-b099cdf014b2|Archive Ontologically (composite)]]
(RFC 78c2b7d0 C5). The only difference is the value-source of step 1:
`targetValueQuery` (NamedQuery → archive ontology) there, `targetValueSubstitution`
(`$input.ontology` → user pick) here.
